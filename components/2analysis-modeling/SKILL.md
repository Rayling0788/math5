# 赛题分析与建模设计

## 数学建模规范参考

如需领域判断，读取 `../_references/math_modeling_norms.md` 中的“赛题理解与子问题识别”“假设与模型建立”和“题型防错速查”小节。该文件只作为规范知识库，不替代本阶段的分析报告结构。

## 必须产出

在当前工作目录的 `reports/` 子目录中创建或更新：

- `reports/ANALYSIS_MODELING_REPORT.md`：
  - 赛题分析、子问题拆解、数据与附件理解、评价标准、关键歧义和假设预检。
  - 变量、符号、模型假设、目标函数、约束条件、求解算法、各子问题实现口径、代码阶段任务清单

不要在本阶段写论文正文，不要生成最终 `paper/`，不要把图表排版任务提前到这里。


## 工作流程

先读取 `plan.md` 的执行模式。`delivery` 模式优先形成可运行的简化合同，不把高保真研究写成代码阶段的硬前置。


### Step 1: 子问题拆解

只把题面中明确编号的顶层问题当作子问题，例如“问题一/二/三”“Problem 1/2/3”。不要把小问、背景描述、数据说明、提交要求误当成独立子问题。

在 `ANALYSIS_MODELING_REPORT.md` 开头明确写：

根据题目动态调整问题数量

本赛题共 X 个子问题。

每个子问题要说明：

- 输入数据和已知条件。
- 要求输出及其数学、物理或决策本质。
- 决策变量或预测对象。
- 目标函数或评价指标。
- 约束条件。
- 与其它子问题的依赖关系。
- 关键难点、不确定性或可辨识性风险。
- 至少一个可信备选方法（确有选择空间时）、适用条件、优缺点与拒绝理由。
- 所选方法为何匹配题目材料、附件证据、数据规模、机理、精度和验证能力。
- 绘制哪些图像或表格来展示结果。
- 该问是否存在真实迭代、判定分支、失败回退、多初值筛选或停止条件；只有这些逻辑用图比公式和文字更清楚时，才规划局部算法流程图。无需为省略逐问流程图逐一辩解。
- 是否需要由 MATLAB 生成参数化模型示意图，以及图中应显示的真实几何、坐标系、局部基向量、尺寸和关键约束。
- 最小可运行模型、预期证据等级和秒级烟雾测试。
- 可选高保真升级、其额外收益、预算上限，以及失败时保留哪个快速层结论。

上述内容必须按“问题一分析”“问题二分析”等独立小节完整展开，不能只写一段总体路线后直接跳到公式。分析小节服务于后续论文的“问题分析”章节，但不在此提前编造结果。

### Step 2: 假设敏感性预检

列出关键歧义，不要急着定模型。重点检查会改变比较对象、固定端点、可移动边界、参数自由度、时间原点、成本口径或下游路径的表述。对每项歧义区分：题面字面口径、常见竞赛解释，以及必要时更严格的工程口径；更严格不等于更符合题意，不得用自定义的“公平口径”静默替换题面目标。

歧义采用分级处理：

1. 若题面文字、附图、上下问依赖或简单验算已明显支持一种解释，选择该主解释，并记录其他解释及排除理由，不要求重复求解。
2. 若另一解释只影响次要数值而不改变结论，可把它列为解释敏感性检查，给出影响方向或有界比较。
3. 若两种解释均有充分依据，且会翻转“能否优化/是否可行/谁更优”等核心答案或显著改变推荐值，必须显式披露两种口径。主口径完整求解；另一口径可完整求解，也可用解析证明、不变量或反例完成，只要足以支撑对应结论。只有实际分别执行的数值分支才建立独立 `scenario_key`。

对于路线或几何优化，至少逐项登记：所比较的长度或成本包含哪些路段、端点是否固定、切入/切出位置能否移动、半径比等参数是否固定、路径必须位于哪个区域，以及下游问题采用哪条路径。若这些选择改变后续速度、容量、成本或安全结论，下游必须继承相同的 `scenario_key`，不得跨口径拼接结果。

必须在 `ANALYSIS_MODELING_REPORT.md` 中包含：

```markdown
## 假设敏感性预检

### 模糊表述、解释候选与题面依据
...

### 快速验算与逻辑递进性检查
...

### 主解释、排除理由与适用范围
...

### 需要并列保留的解释场景或解析分支
...

### 绘制的图像和对比表格


```

如果某个假设会让后续问题的新增条件没有边际效果，要回头调整解释.

### Step 3: 数据理解与建模路线

对每份附件做数据理解：

- 行列规模和字段解释。
- 缺失、异常、重复、单位不一致。
- 可直接用于建模的变量。
- 需要派生的指标。

然后给出一张覆盖题面与附件输入、数据处理、问题依赖、模型、求解、验证和最终决策的总体技术路线节点合同：

```text
题面 -> 数据清洗(EDA) -> 子问题一模型 -> 子问题二模型 -> 。。。。 -> 结果检验 -> 论文展示
```

不要再为每个顶层问题机械复制流程图。逐问只记录图型决策：跨问题依赖归入总体路线图；局部迭代、分支、回退和停止判定可绘制算法流程图；几何、机构、接触、边界与尺寸关系使用 MATLAB 或 TikZ 构型图；数值规律与结论使用 MATLAB 数据图；单向递推使用公式和文字。局部流程图若保留，只覆盖“初始化 -> 更新 -> 判定 -> 回退/循环 -> 停止 -> 输出”的真实执行逻辑，并放在对应模型求解小节。

### Step 4: 建模报告

在 `ANALYSIS_MODELING_REPORT.md` 中写出可交给代码阶段实现的完整方案。

每个子问题至少包含：

- 问题目标。
- 问题本质、关键难点、备选模型比较与选型理由。
- 符号和变量。
- 模型假设。
- 目标函数。
- 约束条件。
- 求解方法。
- 输入输出。
- 代码实现要点。
- 结果校验方法。

若存在会改变核心结论的解释分支，还必须为每个保留口径写清目标函数、比较对象、固定端点、可移动边界、参数自由度、适用范围、求解或证明方式，以及传给下游的场景键。不得把不同口径的目标值放在同一排名或同一推荐结论中比较。

公式要清楚到代码阶段能直接实现。算法描述要包含核心步骤、停止条件、复杂度或可行性说明。

对含多组方程、递推、分段状态或优化约束的问题，在建模报告中同时给出“模型汇总合同”：列出正文最终应集中保留的几何/状态方程、目标函数、约束、边界条件、索引范围和待求变量。汇总只收录代码实际使用的核心关系；完整推导仍以前一单元、一个路径段或一个局部事件为例展开，不能用汇总块代替推导。

每个机制复杂的问题还要给 Writer 一份“读者推导合同”。该合同不是公式清单，而是说明：题目当前要找什么；先观察哪个具体把手、板凳、路径段、样本或候选；哪些量已知、哪个量未知；依据哪一条可看见的几何、物理或统计关系得到第一条方程；这条方程先求出什么；为什么下一步要推广或分类；最后怎样转成代码实际使用的统一模型。几何题优先给出“局部构型/辅助线关系 -> 标量或初等几何式 -> 坐标或向量式”的双层表达，避免把决策向量、统一下标或约束集合当作读者第一次接触模型的入口。

若现有模型只能给出数值算法而无法解释上述局部关系，必须把它登记为写作证据缺口并补足推导；不得把“算法可运行”误当成“解法可讲清”。这项补充可以是等价的符号推导、局部小算例或由真实参数生成的构型图，不要求重新计算已经接受的结果，但不得改变原模型含义。

对几何、机构、碰撞或曲线路径问题，还要在建模报告中给出“MATLAB 局部机理图合同”。明确需要展示的真实曲线段、刚体轮廓及姿态、带下标关键点、连接点、圆心或切向基准、运动方向，以及余弦定理、投影、相切或距离约束所需的辅助线。优先规划正视二维局部放大图并保持真实比例；只有第三维确有模型含义时才改用 3D。若不同构型对应不同推导，可设计成并排多面板，但每个面板都必须由同一组模型参数计算得到。

同时维护一张统一假设登记表，字段至少包括 `assumption_id`、假设内容、依据、适用问题、作用、失效条件和敏感性处理。建模报告可在逐问合同中引用假设 ID，但论文写作阶段必须将全部共同和特有假设汇总到唯一的一级“模型假设”大节。不得为了显示创新机械叠加 AHP、CRITIC、PSO、BP、LSTM 等模型；复杂度必须由题目证据和验证收益支撑。

每个问题必须拆成两层合同：

- `fast_contract`：能在当前预算内真实执行，并以根 Skill 的交付质量底线为验收目标；必须使用相关附件真实字段、完整回答题问，包含边界、量纲、独立基线、参数来源和敏感性检查。仅跑通、趋势演示或代表性参数替代不得标为 `PAPER_USABLE`；
- `certification_upgrade`：仅在其能实质改变结论或用户选择 `certification` 时进入关键路径。

建立 `results/workflow_edges.csv`。只有数值消费的字段使用 `blocking` 边；高保真 corroboration、额外流程图和文字增强通常使用 `advisory` 边。不要因为问题编号相邻就默认串行依赖。

推荐结构：

```markdown
# 建模报告

## 1. 总体建模框架
## 2. 数据处理方案
## 3. 符号说明
## 4. 问题一模型
## 5. 问题二模型
## 6. 问题三模型
    .... 
## 7. 灵敏度分析与检验方案
## 8. 代码实现任务清单
```

如果子问题数量不是 3 个，按实际题面调整章节，不要硬凑。

### Step 5: 给代码阶段的接口

在 `ANALYSIS_MODELING_REPORT.md` 末尾写一个“代码实现任务清单”，格式如下：

```markdown
## 代码实现任务清单

| 任务 | 输入 | 输出 | 方法 | 校验 |
| --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... |
| 问题二 | ... | ... | ... | ... |
```


## 质量要求

- 所有结论都能回到题面或数据。
- 不编造数据字段和数值。
- 不跳过歧义分析。
- 不跳过逐问的问题本质、难点、备选方法和选择理由。
- 复杂问题必须同时具备代码合同和读者推导合同；后者能从一个具体对象说明公式怎样产生、先求出什么以及如何推广。
- 不使用未经适用性和基线验证的模型堆叠替代真实推理。
- 模型既要有数学表达，也要能被代码实现。
- 若数据不足或题面不清，要明确记录风险和替代方案。
- `delivery` 模式下，20% 总预算或连续两次失败仍未通过的高保真门禁必须降级为 `FAILED_DIAGNOSTIC`，不得继续阻塞快速合同。
